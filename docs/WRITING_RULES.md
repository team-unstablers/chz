# docs/ 문서 작성 룰

이 문서는 `docs/` 바로 아래의 **번호 스펙 문서**(`NN-주제.ko.md`)에 적용되는
작성 규칙을 정의합니다.

## 적용 범위

- **적용 대상**: `docs/` 바로 아래의 번호 문서 (예: `60-realize-intro.ko.md`)
- **적용 제외**:
  - `docs/idea-sketches/` — 자유로운 메모장입니다. 형식·문체·구조 어떤 규칙도
    적용받지 않습니다.
  - 이 문서(`WRITING_RULES.md`) 자체는 번호 체계 밖에 둡니다.

## 독자와 문체

- **주요 독자**: 컴퓨터에 관심 있는 비-개발자, 그리고 소프트웨어 개발을 시작한 지
  얼마 되지 않은 초보 개발자입니다.
- 가급적 **부드러운 말투(존댓말)** 와 **쉬운 용어**를 사용합니다.
- 어려운 CS 용어는 최대한 풀어서 설명합니다. 쉬운 용어로 대체하는 것이
  부적절하다고 판단되면, **쉬운 예제를 먼저 보여준 뒤** "이런 걸 ○○(용어)라고
  합니다"처럼 용어를 나중에 소개합니다.
- 예시는 **흥미 위주**로 작성합니다. 게임이나 일상 생활에서 접할 수 있는 문제를
  소재로 삼습니다. (예: 크리티컬 판정, 예금 이자 계산)

## 파일 이름과 번호

- 파일 이름은 `NN-주제.ko.md` 형식입니다. 주제(slug)는 영어 소문자
  kebab-case로 씁니다.
- `.ko.md`는 **한국어 원본**임을 나타냅니다. 번역본이 생기면 `NN-주제.en.md`처럼
  나란히 두되, 원본(`.ko`)이 항상 우선하며 번역본에는 동기화 의무가 없습니다.
- 번호는 아래 배정표를 따릅니다. 새 문서는 해당 번호대에서 비어 있는 다음 번호를
  사용합니다.

| 번호대  | 주제                                              |
|--------|--------------------------------------------------|
| 00–09  | 개요 · 비전 · 철학 · 용어집                          |
| 10–19  | 언어 문법 (키워드, 구문, TS 슈퍼셋 규칙)               |
| 20–29  | 컴파일러 · 빌드 (`chz build`, 전처리, tsc 연동)        |
| 30–39  | 계약 · 검증 (`ensure`, `precondition`, 테스트)       |
| 40–49  | 리소스 (`imagine resource`, 생성 자산)               |
| 50–59  | 프로파일 · 런타임 (`@profile`, 캐퍼빌리티 경계)         |
| 60–69  | realize (파이프라인, Realizer, 의존성 그래프)         |
| 70–79  | 툴링 (CLI, IDE, LSP)                              |
| 80–89  | (예비)                                            |
| 90–99  | 메타 (로드맵, 결정 기록 인덱스 등)                     |

- 배정표를 바꿔야 한다면(주제 추가·변경), 새 문서를 만들기 전에 이 표를 먼저
  갱신합니다.

## 문서 간 상호 참조

- 다른 번호 문서를 본문에서 **처음 언급할 때만** 마크다운 링크를 겁니다:
  `[62 문서](62-realize-dependency-graph.ko.md)`
- 같은 문서 안에서 두 번째 언급부터는 링크 없이 "62 문서"라고만 씁니다.
- 코드 블록 안의 주석에서는 링크를 걸지 않습니다. (렌더링되지 않습니다.)

## 코드 예제

- Cheese 코드(`imagine` / `ensure` 등 확장 키워드를 포함하는 `.chz.ts`)는
  ` ```typescript chz ` 태그를 사용합니다.
- 순수 TypeScript(realize 산출물, 인터페이스 정의 등)는 ` ```typescript `를
  사용합니다.
- 첫 토큰이 `typescript`이므로, 두 경우 모두 GitHub에서 구문 하이라이팅이
  유지됩니다.
- 파일 맥락이 있는 예제는 첫 줄에 `/// 파일명` 주석을 붙입니다. 일부만 발췌한
  경우 `/// battle.chz.ts (발췌)`처럼 표기합니다.

## 정하지 않기로 한 것

다음 항목은 논의를 거쳐 **의도적으로 규칙을 두지 않기로** 결정했습니다.
(재논의 전까지는 다시 고민하지 않습니다.)

- **헤딩 레벨 구조** — `#` 개수나 섹션 깊이는 문서마다 자유입니다.
- **문서 상단 메타 블록** — 상태 표시 등의 메타 블록을 두지 않습니다.
  (히스토리는 git이 기억합니다.)

## 문서의 지위와 유지보수

- 코드와 문서가 다르면, 문서가 더 최신일 가능성이 높습니다. (CLAUDE.md에도
  명시되어 있습니다.)
- 설계 결정이 바뀌면 해당 스펙 문서를 먼저 갱신합니다.
- 이 룰이 개정되면 기존 문서도 함께 정비하는 것을 원칙으로 하되, 기계적으로
  적용 가능한 항목(상호 참조 링크, 코드 태그)부터 우선 적용합니다.
