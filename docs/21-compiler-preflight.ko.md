# 치즈는 여러분의 코드를 어떻게 읽나요

치즈기여어 파일에는 두 가지가 섞여 있습니다. 여러분이 직접 쓴 평범한
TypeScript와, `imagine`으로 선언한 계약입니다. 컴파일러는 이 둘을 갈라
읽어야 합니다.

이 문서는 그 과정을 설명합니다. 당장 코드를 쓰는 데 꼭 필요한 내용은
아니지만, **오류 메시지가 왜 그렇게 생겼는지**, 그리고 **왜 어떤 오류는
realize를 아예 시작조차 못 하게 막는지**를 이해하는 데 도움이 됩니다.

## 문법을 두 번 만들지 않기로 했습니다

치즈기여어는 TypeScript의 슈퍼셋입니다. 그러니 컴파일러는 TypeScript 전부를
읽을 수 있어야 합니다. 제네릭도, 조건부 타입도, 정규식 리터럴도, 중첩된
템플릿 문자열도 전부요.

TypeScript 문법은 크고, 지금도 계속 자라고 있습니다. 그것을 치즈기여어가
따로 한 벌 더 구현하면, TypeScript가 새 문법을 추가할 때마다 뒤따라가야
하고 두 구현이 조금씩 어긋나기 시작합니다. 그래서 치즈기여어는 이렇게
나눴습니다.

> **치즈기여어는 자기가 추가한 껍데기만 읽습니다. 나머지는 전부 TypeScript가
> 읽습니다.**

치즈기여어가 직접 읽는 것은 네 가지뿐입니다.

- `@profile` 지시문
- 최상위의 `imagine function` / `imagine class`
- imagine 클래스 안의 imagined 멤버
- 계약 본문에서 `requirements` / `ensure` 문장의 경계

함수의 매개변수와 반환 타입, 계약에 쓴 식, `import`와 `export`, 이름이
무엇을 가리키는지 — 이런 것은 전부 TypeScript의 몫입니다. 자세한 문법은
[10 문서](10-imagine-grammar.ko.md)를 참조하십시오.

## `imagine`을 지우는 대신, 자리를 남깁니다

TypeScript는 `imagine`이라는 단어를 모릅니다. 그러니 TypeScript에게 넘기기
전에 뭔가 손을 봐야 합니다.

가장 단순한 방법은 imagine 선언을 통째로 잘라내는 것입니다. 실제로 예전
치즈기여어가 그렇게 했습니다. 그런데 이 방법에는 문제가 있습니다.

**잘라내면 위치가 어긋납니다.** 15번째 줄에 있던 코드가 잘라낸 뒤에는 9번째
줄이 됩니다. TypeScript가 "9번째 줄에 오류가 있습니다"라고 알려주면,
여러분에게는 15번째 줄이라고 다시 번역해서 알려줘야 합니다. 번역이 조금만
어긋나도 엉뚱한 줄을 가리키게 됩니다.

**그리고 잘라낸 뒤에는 검사할 수 없습니다.** 문법이 틀린 imagine 선언을
잘라내 버리면, 틀렸다는 사실 자체가 같이 사라집니다.

그래서 지금은 자르지 않고 **같은 자리에 같은 길이의 다른 것을 놓습니다.**

```typescript chz
imagine function 점수계산(콤보: number): number {
  requirements(`콤보 수에 비례해 점수를 계산합니다.`);
}
```

TypeScript에게는 이렇게 넘어갑니다.

```typescript
declare function 점수계산(콤보: number): number ;

```

두 가지가 일어났습니다.

**하나.** `imagine`이 `declare`로 바뀌었습니다. 우연히도 둘 다 일곱 글자라
글자 수가 그대로입니다. `declare`는 TypeScript에게 "이런 것이 있다고 치되,
구현은 다른 데 있다"는 뜻입니다. `imagine`이 하려는 말과 정확히 같습니다.

**둘.** 계약 본문이 세미콜론 하나와 공백으로 바뀌었습니다. `declare`로
선언한 것에는 본문이 올 수 없으니까요.

바뀐 결과는 **글자 수도 줄 수도 원본과 똑같습니다.** 그래서 TypeScript가
알려주는 위치를 번역 없이 그대로 쓸 수 있습니다. 어긋날 일이 없습니다.

이렇게 해 두면 TypeScript는 `점수계산`이 "숫자 하나를 받아 숫자를 돌려주는
함수"라는 것을 **아직 구현이 없는데도** 알게 됩니다. 그래서 여러분이 사람
코드에서 `점수계산(3)`을 호출하면 타입 검사가 제대로 됩니다.

### 지워 버린 계약은 어디로 가나요

방금 계약 본문을 세미콜론으로 덮어 버렸습니다. 그런데 그 안에 적힌
`requirements(...)`와 `ensure(...)`는 읽어야 합니다. LLM에게 넘길 내용이고,
`ensure`는 실제로 테스트로 만들어야 하니까요.

그래서 치즈기여어는 **종이를 한 장 더 씁니다.** 이쪽 종이에는 계약만 원래
자리에 남기고 나머지를 전부 지웁니다.

- **첫 번째 종이** — 선언의 모양을 읽습니다. 무슨 타입인지, 어떤 이름인지.
- **두 번째 종이** — 계약의 내용을 읽습니다. 무엇을 요구했고, 무엇을
  확인해야 하는지.

두 번째 종이가 필요한 자리는 세 군데입니다.

```typescript chz
imagine class 카운터 {
  requirements(`카운터를 관리합니다.`);      // ← ① 클래스 본문의 계약

  imagine readonly 점수: number {
    requirements(`현재 점수입니다.`);        // ← ② 프로퍼티의 계약 본문
  }

  imagine 증가(): void {
    requirements(`점수를 1 올립니다.`);      // ← ③ 함수·메서드의 계약 본문
  }
}
```

①은 클래스 본문 한가운데에 문장이 있는 것이고, ②는 프로퍼티 타입 뒤에
중괄호가 오는 것입니다. 둘 다 TypeScript 문법에는 없는 모양입니다. ③은
모양 자체는 평범하지만, 위에서 본 것처럼 `declare` 선언에는 본문이 올 수
없어서 지워집니다.

두 종이 모두 원본과 글자 수가 같습니다. 그래서 **어느 쪽에서 찾은 것이든
위치는 언제나 여러분의 원본 파일 기준**입니다.

## 오류가 있으면 아무것도 만들지 않습니다

여기서 순서가 중요해집니다.

realize는 파일을 여럿 만듭니다. `chz/realization/` 아래에 디렉토리를 만들고,
사람이 쓴 코드를 복사해 넣고, 그다음 LLM에게 구현을 부탁합니다.

예전에는 이 순서가 뒤집혀 있었습니다. **소스를 다 검사하기 전에 디렉토리를
만들고 파일을 썼습니다.** 그래서 여러분이 오타를 하나 냈을 때, 오류를 보기
전에 이미 디렉토리가 생기고 파일이 반쯤 쓰여 있었습니다.

지금은 이렇습니다.

```text
파일을 읽는다
  ↓
치즈기여어 문법을 읽는다
  ↓
TypeScript에게 넘겨서 읽힌다
  ↓
오류를 모아 원본 위치로 되돌린다
  ↓
오류가 하나도 없을 때만 ── 디렉토리를 만들고, 파일을 쓰고, LLM을 부른다
```

문법 오류가 있으면 **디렉토리도 생기지 않고, LLM도 불리지 않습니다.**
LLM을 부르는 데는 시간과 비용이 드니, 고칠 수 있는 오류라면 부르기 전에
알려 드리는 편이 낫습니다.

오류는 **한 번에 모아서** 보여 드립니다. 첫 번째 오류에서 멈추고 고치면
두 번째 오류가 나오는 식이 아니라, 한 번 돌려서 알 수 있는 만큼을 함께
알려 드립니다.

그리고 `chz realize`, `chz realize --dry-run`, `chz realize --json`은 **같은
검사를 씁니다.** 셋이 다른 답을 내놓는 일은 없습니다.

## "아직 없는 것"과 "잘못 쓴 것"을 가릅니다

치즈기여어에는 재미있는 규칙이 하나 있습니다. **쓰는 순간 계약이
생깁니다.**

```typescript chz
imagine class 게임 {
  requirements(`간단한 게임을 관리합니다.`);
}

const 게임하나 = new 게임();
게임하나.시작();   // 아직 만들지 않은 메서드
```

`시작()`은 아직 어디에도 없습니다. 보통의 TypeScript라면 "그런 속성은
없습니다"라는 오류(`TS2339`)가 납니다. 하지만 치즈기여어에서는 오류가
아니라 **LLM에게 주는 숙제**입니다. 여러분이 그것을 썼다는 사실 자체가
"이걸 만들어 주세요"라는 요청이니까요.

그런데 똑같은 오류가 진짜 실수일 때도 있습니다.

```typescript
const 사용자 = { 이름: "렌", 나이: 14 };
console.log(사용자.이름름);   // 오타
```

이것도 `TS2339`입니다. 하지만 이건 숙제가 아니라 그냥 오타입니다.

### 오류 번호가 아니라 주인을 봅니다

그래서 치즈기여어는 **오류 번호로 가르지 않습니다.** 번호로 가르면 위의
오타가 조용히 LLM의 숙제 목록으로 넘어가 버립니다. 오타를 고쳐 달라고
LLM에게 부탁하게 되는 셈이죠.

대신 **그 오류가 가리키는 것의 주인**을 봅니다.

1. 오류가 난 자리가 `무언가.속성` 형태인가?
2. 그 "무언가"의 타입을 따라갔을 때, `imagine` 선언에 닿는가?

둘 다 맞을 때만 숙제입니다. 나머지는 전부 사람이 고쳐야 할 오류입니다.

`게임하나.시작()`은 `게임하나`의 타입이 `imagine class 게임`이므로 숙제가
됩니다. `사용자.이름름`은 `사용자`가 여러분이 만든 평범한 객체이므로
오타입니다.

### 사람이 고칠 오류는 LLM을 부르지 않습니다

이 구분이 실제로 하는 일이 있습니다.

사람이 쓴 코드에 오류가 있으면, **LLM을 한 번도 부르지 않고** realize가
즉시 실패합니다. 오류 위치는 여러분의 `.chz.ts` 파일 기준으로 알려 드립니다.

이유는 단순합니다. LLM은 여러분이 쓴 코드를 고칠 수 없습니다 — 고쳐서도 안
되고요. 사람 코드가 깨져 있으면 LLM이 아무리 좋은 구현을 만들어도 검증은
계속 빨간불입니다. 그런 세션은 시작하기 전부터 이길 수 없습니다. 그러니
시작하지 않는 편이 낫습니다.

## 오류 번호 읽기

| 앞자리 | 무엇에 대한 오류인가 | 누가 고치나 |
|---|---|---|
| `CHZ1xxx` | 치즈기여어 문법 | 사람 |
| `CHZ2xxx` | 계약의 모양 | 사람 |
| `CHZ3xxx` | realize·프로파일 등 정적 규칙 | 사람 |
| `TSxxxx` | TypeScript가 알려준 오류 | 대개 사람, 일부는 LLM의 숙제 |

`CHZ`로 시작하는 오류와 TypeScript의 **문법** 오류는 언제나 realize를
막습니다. 숙제로 승격되는 것은 위에서 설명한 조건을 만족하는 일부
`TSxxxx` 오류뿐입니다.

모든 메시지에는 어떻게 고치면 되는지가 함께 적혀 있습니다.

## 여기서 만든 것을 모두가 나눠 씁니다

읽기가 끝나면 치즈기여어는 하나의 분석 결과를 갖게 됩니다. 이 결과를 뒤의
모든 단계가 나눠 씁니다.

- 어떤 심볼이 어떤 심볼을 필요로 하는지 알아내는 의존성 그래프
  ([62 문서](62-realize-dependency-graph.ko.md))
- 사람 코드를 prologue와 epilogue로 나누는 단계
  ([60 문서](60-realize-intro.ko.md))
- 사람 코드의 상대 경로를 다시 쓰는 단계
  ([20 문서](20-module-resolution.ko.md))
- LLM에게 넘길 계약을 정리하는 단계

이들 중 **어느 것도 소스 문자열을 다시 읽지 않습니다.** 한 번 읽은 결과를
받아 쓸 뿐입니다. 같은 코드를 여러 곳에서 제각각 해석하면, 문법이 자랄 때
서로 다른 답을 내놓기 시작하기 때문입니다.
