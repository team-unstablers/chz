# 치즈 (Cheese, `.chz`) — 바이브 코딩을 위한 프로그래밍 언어 (구상)

> **상태**: 구상 / 설계 논의 단계 — **living document** (논의 진행에 따라 수시 갱신)
> **개시**: 2026-07-23 새벽 (텔레그램 세션)
> **참여**: unstabler (구상·결정) / 렌 (설계 리뷰·문서 정리)

## 1. 비전

"바이브 코딩을 위한 범용 프로그래밍 언어"

- **LLM이 쓰고, 사람이 감독하기 위한 언어**
- 템플릿 엔진 내장
- 최대한 쉬운 도큐멘테이션

사람은 의도(스펙·계약·감독)를, LLM은 구현을 담당한다. 이 역할 분담을 관례가 아니라 **언어 문법과 컴파일러가 강제하는 구조**로 만드는 것이 핵심 차별점이다.

## 2. 핵심 개념 (원 구상 스케치)

### 2.1 `@profile` — 프로파일 선언

```chz
// 언어 프로파일을 'console'으로 마킹함, 콘솔 관련 IO 모듈이 자동으로 로드됨
@profile console

이름 = input(prompt: "이름을 입력하세요!")
say("안녕하세요, {이름}님!")
```

- 문자열 보간, 한국어 식별자를 기본 지원한다.

### 2.2 `imagine` / realize

- `imagine` 키워드: 사람이 함수·클래스·모듈의 **시그니처와 requirements(자연어 요구사항)만 선언**한다.
- **realize**: 빌드 단계에서 LLM 기반 code resolver가 imagine 심볼의 **구현체·typedef·유닛 테스트를 emit**하는 과정. 디펜던시 그래프에 따라 다르나, 일반적으로 realize 과정에서 유닛 테스트가 성공해야 한다.

```chz
// 일반 함수
func add(a: int, b: int) -> int {
    return a + b
}

// 'imagine' 키워드를 사용한 함수 정의
// 사람이 구상한 함수, 빌드 단계에서 LLM이 이를 구현한다
imagine func 충돌판정_2D(도형A: Shape, 좌표A: Point, 도형B: Shape, 좌표B: Point) -> bool {
    두 도형 간 충돌 판정을 수행합니다.
}

// 'imagine' 키워드는 class나 module 단위로도 동작한다.
imagine class 비행기슈팅게임 {
    requirements"""
        비행기 슈팅 게임을 구현합니다.
            - SDL을 사용합니다.
            - 리소스는 알아서 생성합니다.
            - 갤러그같은 무한 루프 가능한 게임을 만들어 주세요.
    """

    required imagine func toggleFullscreen() {
        requirements"""
            이 함수를 호출하면 전체 화면을 토글할 수 있어야 합니다
        """
    }

    required imagine var isFullscreen: bool {
        requirements"""
            이 computed 변수를 통해 전체 화면 여부를 확인할 수 있어야 합니다
        """
    }

    required imagine var score: int
    required imagine var remainingLives: int
}

let game = 비행기슈팅게임()
game.start()
```

### 2.3 `required` 제약 — "사용처가 계약을 만든다"

- `required imagine func/var` 로 필수 심볼 제약을 명시할 수 있다.
- **참조만으로도 제약이 발생한다**: imagine class/module의 아직 존재하지 않는 심볼을 참조하면(`game.start()`) 해당 심볼에 컴파일 타임 required 제약이 걸리고, LLM은 반드시 이를 구현해야 한다.

### 2.4 realize 산출물의 버전 관리

- LLM은 일관된 결과를 내놓을 수 없으므로, realize된 구현체는 재현성을 위해 git 저장소에 함께 커밋하는 것을 전제로 한다.

### 2.5 `imagine resource` — 생성형 리소스 (2026-07-23, 인트로 초안에서 추가)

- 코드뿐 아니라 **에셋(이미지·오디오 등)도 생성형 AI에게 요구**할 수 있다. "LLM이 만들고 사람이 감독"을 코드 너머 리소스까지 확장하는, 선행 사례(§7) 어디에도 없는 고유 차별점.

```chz
imagine resource alienSprite: Chz.ImageAsset {
  width = 64;
  height = 64;

  requirements(`외계인 적 캐릭터 스프라이트를 생성하십시오. 귀엽고 만화적인 스타일이어야 합니다.`);
};
```

- **선언형 프로퍼티**(`width = 64`, `maxDuration = 1.0` 등)가 생성 파라미터인 동시에 산출물 검증 조건이 된다. 부등식류 제약도 타입별 제약 프로퍼티(`maxDuration` 등)로 표현한다. 산출물은 `resources/` 디렉토리에 emit.
- (초안 초판은 `required resource` + `ensure(predicate)` 형태였으나 §4.6·§4.7 해소 과정에서 현재 형태로 확정.)

### 2.6 표기·산출물 구조 (인트로 초안 `docs/00-chz-intro.ko.md` 기준)

- **`requirements()`는 옵셔널** — 명시하면 정확도가 오르지만, 시그니처만으로도 realize 가능.
- **파일 확장자 `.chz.ts`** — TS 툴링(하이라이팅 등)에 공짜로 편승. 단, 순정 에디터/tsc가 `imagine` 키워드에 오류를 표시하는 트레이드오프 있음 (LSP 래퍼로 해소 예정, §5 구현 전략 3).
- **realize 산출물 레이아웃**: `chz/realization/<file>/` 아래 —
    - `implementation.ts` (진입점) / `implementations/` (심볼별 구현)
    - `tests/*.ensure.ts` (사람이 작성한 계약) vs `tests/*.autogen.ts` (LLM 자체 작성 테스트) — **§4.2 셀프 채점 문제를 파일 구조 레벨에서 물리적으로 분리**
    - `resources/` (생성형 에셋, §2.5)
    - `realization-cache.json` (증분 realize 캐시 — §3의 lockfile 모델에 대응)
- **언어명(잠정)**: '치즈기여어 (Cheese Contribution Language)'.

## 3. 설계 원칙 (논의로 도출)

1. **빌드는 절대 LLM을 호출하지 않는다.** `chz realize`는 개발 시점의 초안 작성 도구이고, 빌드/CI는 언제나 커밋된 realized 코드로만 동작한다. → 재현성 문제 해소, 오프라인 빌드 가능, 모델 deprecation에 면역.
2. **lockfile 모델.** imagine 블록 = `package.json`의 버전 범위, realized 코드 = lockfile에 대응. realize 결과에 모델/프롬프트 해시를 메타데이터로 남겨 provenance를 확보한다.
3. **감독 가능성 우선.** 언어의 정체성은 "사람이 감독"에 있으므로, 설계 결정은 diff 가독성·계약 명시성·가정의 가시화를 우선한다.

## 4. 미해결 설계 문제

### 4.1 incremental realize (재-realize 단위)

requirements 일부 수정 시 심볼 전체가 재생성되면 diff가 통째로 갈려 감독이 불가능해진다. 이전 구현을 컨텍스트로 제공하고 **최소 diff로 패치**하는 방식이 필요. 해시 기반 캐싱 + 심볼 단위 무효화.

### 4.2 셀프 채점 문제와 `ensure` 계약 (제안)

LLM이 구현과 테스트를 모두 작성하면, 테스트는 사람의 의도가 아니라 LLM의 해석을 검증하게 된다. → requirements 옆에 **사람이 직접 작성하는 예시 계약(`ensure` 절)** 문법 도입: 예) `ensure 충돌판정_2D(겹치는 두 원) == true`. 자연어 requirements + 예시 계약의 조합이 실질 인터페이스가 된다.

### 4.3 드리프트 시맨틱 (해결, 2026-07-23 — 상세: `docs/60-realize.ko.md`)

사람이 realized 코드를 직접 수정했을 때의 정본 문제 (codegen 라운드트립의 고전 문제). 원 제안은 "사람 편집 우선 + 심볼 전체 stale 마킹"이었으나, 블록 단위 공존 모델로 발전시켜 해결.

**→ 해결: 3단 정책**

1. **마커 편집** — `// @chz-realize-override` 주석이 **바로 다음 statement 하나**를 사람 소유로 고정 (여러 문장은 JS 블록 `{ }`으로 그룹핑, 마커 뒤 `: 설명`으로 의도 병기 가능). 새 statement 삽입과 생성된 statement의 수정·전환 모두 지원. 경계가 주석 위치가 아닌 AST 기준이라 포매터에 안전하고, 블록 스코프가 'LLM 생성 코드는 오버라이드 내부에 의존 불가'라는 격리를 공짜로 강제. LLM은 고정 statement를 수정·삭제할 수 없으며 재-realize 시에도 보존.
2. **무단 드리프트** — `realization-cache.json` 해시로 감지. 해당 심볼은 재-realize에서 제외(사람 편집 우선) + 경고. `chz realize --adopt`로 마커를 자동 부착하여 정식 오버라이드로 편입.
3. **계약과 충돌 시** — 기본은 계약 승리: ensure 테스트는 오버라이드 포함 최종 코드에 실행되고, 실패하면 빌드 실패 ('사람이 작성한 의도끼리의 모순'을 드러냄). `--skip-tests`류 옵션을 명시하면 편집이 임시 우선 (경고 동반).

### 4.4 ASSUMPTIONS 리포트 (감독 UX)

realize가 코드만이 아니라 "요구사항을 어떻게 해석했고, 어느 부분이 애매해서 어떤 가정을 했는지"를 리포트로 함께 emit한다. 애매함이 조용히 해소되지 않고 사람 눈에 보이게 하는 장치.

- **(2026-07-23 구체화) 감사 지향 주석 정책** — 리포트와 별개로, realize 산출물 자체도 감사를 위한 주석을 필수 포함한다: 요구사항 해석·계약 대응을 요약하는 doc comment + 각 단계를 설명하는 상세 주석 + 애매했던 지점의 인라인 `ASSUMPTION:` 주석. LLM의 목표는 '동작하는 코드'가 아니라 '**사람이 감사할 수 있는 코드**'다. 인라인 주석은 코드 리뷰 동선에서, 리포트는 전체 조망에서 같은 정보를 노출한다. (예시: `docs/60-realize.ko.md`)

### 4.5 `@profile` = capability 경계 (제안)

`@profile`을 단순 모듈 자동 로드가 아니라 **realize된 코드의 권한 경계**로 사용 (예: console 프로파일에서는 소켓을 열 수 없음). "쉬운 언어" 축과 "감독" 축이 하나의 설계로 통합되는 지점.

### 4.6 키워드 일관성 — `imagine` vs `required` (해결, 2026-07-23)

인트로 초안에서 클래스 멤버 요구는 `imagine var/function`, 리소스는 `required resource`로 표기됨. 원 스케치의 구분(`required` = 필수 제약, `imagine` = LLM이 산출)과 어긋난다.

**→ 해결**: unstabler가 **`imagine resource`로 통일** — 'LLM(생성형 AI)이 산출하는 것'은 모두 `imagine` 계열로 일관.

### 4.7 `ensure`의 두 형태 — 예시 계약 vs predicate (해결, 2026-07-23)

원 스케치는 구체 예시 계약(`ensure 충돌판정_2D(겹치는 두 원) === true`), 인트로 초안은 predicate 함수(`ensure((args, retval) => boolean)`). 표현력은 predicate가, 가독성·의도 명시성(§4.2의 논거)은 구체 예시가 우위.

**→ 해결: `ensure` 오버로드로 이중 지원.**

- `ensure(fn)` — **기계 검증 predicate**. realize 산출물에 대한 테스트로 실행됨. Eiffel의 `ensure`(= postcondition)와 의미 정합. 구체 예시 계약도 이 형태 안에서 표현 가능.
- ``ensure(`자연어`)`` — **자연어 계약**. LLM이 반드시 autogen 테스트 코드로 변환하여 검증할 의무를 가짐.
- 중간에 predicate의 이름으로 `precondition`이 제안되었으나, `(args, retval)` 검사는 DbC 의미론상 **postcondition**이며 LLM 훈련 prior와 충돌한다는 이유로 반려. **`precondition` 키워드는 향후 입력 제약용으로 예약.**
- 리소스의 제약은 `ensure` 대신 선언형 프로퍼티로 통일 (§2.5).

### 4.8 오버라이드 statement의 위치 앵커링 (미결)

재-realize로 주변 코드가 새로 생성될 때, 고정된 오버라이드 statement의 *내용*은 보존되지만 *위치*(예: 함수 맨 앞의 early-return 가드여야 함)와 상대 순서를 어떻게 보존할지는 미결정. git 패치 적용과 동류의 고전 문제. (§4.3의 해결이 남긴 후속 과제)

## 5. 아키텍처 갈림길 (★ 결정됨 — 중간 언어 + TS 슈퍼셋)

전제(unstabler): LLM의 도움을 받더라도 "쓸만한 범용 언어"를 밑바닥부터 만드는 것은 비현실적 → 현실적 선택지는 아래 둘.
반론(렌): 개인이 감당 못 하는 것은 생태계·런타임·툴링이며, 컴파일러 코어는 사정권. 옵션 A도 생태계를 TS에서 빌리는 구조이므로 이 전제는 A/B의 판별 기준이 되지 않는다.

### 옵션 A — 중간 언어

치즈 문법 유지. 사람의 아이디어 → `chz realize` (LLM 구현) → `chz build` → TypeScript+Web 등으로 트랜스파일.

- 장점: 문법의 주인이 됨. imagine/required/ensure를 컴파일러가 강제. 정체성 유지.
- 단점: 파서·체커·툴링 부담. **훈련 데이터 부재** — LLM은 치즈를 학습한 적이 없으므로, 치즈로 구현까지 작성시키면 품질 저하 ("LLM을 위한 언어인데 LLM이 가장 못 쓰는 언어" 역설).

### 옵션 B — 기생 (호스트 언어 내장)

기존 언어에 문법을 맞춘다. 예시 스케치:

```swift
@imagine("2D 충돌을 체크하십시오")
func 충돌체크_2D(...) -> Bool {
}
```

- 장점: 즉시 시작 가능. 호스트 생태계·에디터 지원을 그대로 활용. LLM이 가장 잘하는 언어로 구현하므로 품질 최대. required는 호스트의 interface/protocol 매핑으로 타입체커가 강제 가능 (tsc 에러 목록을 "LLM 의무 목록"으로 변환하는 접근 포함).
- 단점: 문법 소유권 상실. 컴파일러 강제력이 관례+린터 수준으로 약화. 기존 도구와의 차별점 희석.
- 호스트 후보: TypeScript 데코레이터 (최속) / Swift 매크로 (컴파일 타임 코드 생성 훅 보유 — 기생 중 가장 강력).

### 하이브리드 (렌 추천) — "스펙은 중간 언어로, 구현은 기생으로"

치즈를 **구현 언어가 아니라 스펙/계약 언어로 한정**한다. 사람이 작성하는 것만 치즈 문법(imagine 선언, requirements, `ensure`, 최소 배선 코드)이고, **realize는 치즈 코드가 아니라 처음부터 호스트 언어(TS)를 emit**한다. 옵션 A에서의 변경점은 realize의 산출 언어 단 하나.

- 효과 ①: "쓸만한 범용 언어" 부담 소멸 — 치즈는 스펙 표현력만 갖추면 되므로 작아도 된다.
- 효과 ②: LLM의 읽기/쓰기 비대칭 활용 — 처음 보는 DSL을 *읽는* 것은 쉽고(컨텍스트로 스펙 제공), 처음 보는 언어로 관용적 코드를 *쓰는* 것은 어렵다. 하이브리드에서 LLM은 치즈를 읽기만 하고, 쓰는 것은 TS다.
- 효과 ③: "사람의 언어 ≠ LLM의 언어" 분리가 컨셉("LLM이 쓰고 사람이 감독") 자체의 구현이 된다. 감독자는 구현이 아니라 계약(`ensure`)·ASSUMPTIONS 리포트·테스트 결과를 읽는다. 구현 diff는 깊이 검토할 때만 연다.

### ★ 방향 결정 (확정, 2026-07-23) — 중간 언어 + TypeScript 슈퍼셋

unstabler 제안: **중간 언어의 형태를 취하되, 문법은 TypeScript를 따른다.** TS로의 트랜스파일이 쉬워지고, 사람이 짠 기존 코드를 치즈에 녹이기도 쉽다.

관계의 정확한 형태는 서브셋이 아니라 **슈퍼셋** — TS 코드는 거의 전부 유효한 치즈 코드이며, 치즈는 그 위에 `imagine`/`ensure`/`@profile` 확장을 얹는다. TypeScript가 JavaScript에 취한 전략(기존 코드 유효 + 점진 채택 + 기존 툴링 편승)을 치즈가 TypeScript에 반복하는 구조다.

더 정밀하게는 **"서브셋 위의 슈퍼셋"**:

- **확장은 사람을 위해** — 사람이 작성하는 코드는 TS 전체를 허용 (기존 코드 흡수·npm 생태계 인터롭).
- **제한은 LLM에게** — realize된 코드에만 제한 서브셋을 적용 (`eval` 금지, `any` 금지, `@profile` 밖 API 금지). §4.5의 capability 경계가 집행되는 지점.

이 결정으로 §5의 A/B 딜레마와 하이브리드 제안은 자연스럽게 수렴한다: 문법 소유권(옵션 A의 심장)과 LLM 훈련 데이터·생태계(옵션 B의 근육)를 동시에 확보하며, "치즈=스펙 언어, 구현=TS" 하이브리드의 이점은 슈퍼셋 구조 안에서 그대로 유지된다 (imagine 블록 = 치즈 확장 / realized 코드 = plain TS = 역시 유효한 치즈).

**구현 전략**:

1. 치즈 확장 키워드는 선언 레벨에만 존재 → **선언 레벨 전처리기 + TypeScript 컴파일러 API** 조합으로 컴파일러 성립 (풀 파서 자작 불필요). `chz build` = 확장 스트립 → plain TS → esbuild/tsc.
2. "사용처가 계약을 만든다"(§2.3)는 전처리 후 TS를 tsc로 검사해 얻는 진단 목록(예: `Property 'start' does not exist`)을 **LLM 의무 목록으로 변환**하는 방식으로 구현 — 거의 무비용.
3. 에디터 지원은 TS LSP에 위임하는 얇은 래퍼로 처리.
4. 폴백 경로: 확장 키워드가 부담될 경우 valid-TS 인코딩(데코레이터 + tagged template)으로 후퇴 가능 — 단 이 경우 옵션 B와 동일해지므로 기본 경로는 실제 키워드 확장.

**TS 정렬 문법 스케치**:

```chz
@profile console

const 이름 = await input("이름을 입력하세요!")
say(`안녕하세요, ${이름}님!`)
```

```chz
imagine function 충돌판정_2D(a: Shape, posA: Point, b: Shape, posB: Point): boolean {
  requirements`두 도형 간 충돌 판정을 수행합니다.`
  ensure 충돌판정_2D(원(0, 0, 10), 원(5, 0, 10)) === true
}
```

- 정렬 규칙: `func` → `function`, `-> bool` → `: boolean`, `int` → `number`. 한국어 식별자는 JS/TS가 원래 허용하므로 유지. `say`/`input`은 `@profile`이 주입하는 전역.
- **수용한 트레이드**: "최대한 쉬운 문법" 축은 TS 관용구 수준으로 완화 (named args 등 원 스케치 고유 문법은 v1 이후로 유보). 헬로월드 난이도는 유지됨.
- 선례: **Civet** — 소규모로 유지되는 TS 슈퍼셋 트랜스파일러. 실행 가능성이 증명된 경로.

## 6. v0 스코프 (확정, 2026-07-23)

- **범위**: `imagine function` 하나의 엔드투엔드만. `imagine class`/`resource`, `@profile`, 오버라이드 마커 처리, 드리프트 감지, incremental realize, tsc 의무 목록(§2.3)은 모두 다음 마일스톤으로 유보.
- **파이프라인**: `.chz.ts` 전처리 (선언 레벨 스캔, 풀 파서 없음) → 스펙 객체 추출 → realize (claude CLI 헤드리스 `claude -p`) → 구현 + 테스트 emit (`chz/realization/` 레이아웃, 감사 주석·provenance 헤더 포함) → vitest 그린 시 `realization-cache.json`에 해시 기록.
- **레포 구조**: 단일 패키지 (루트 package.json, `src/`에 CLI·전처리기·realize 엔진, `examples/`에 예제).
- **구현 단계**: ① 스캐폴딩 → ② 전처리기 → ③ realize 엔진 → ④ 검증 루프 → ⑤ `충돌판정_2D` 엔드투엔드 데모.
- **진행 방식**: 렌이 각 단계를 opus 서브에이전트에 위임하고 결과를 감독.
- 첫 마일스톤: `충돌판정_2D` 하나를 `.chz.ts` → realize → 테스트 그린까지 엔드투엔드 (1일 미만 스코프).

## 7. 선행 사례와 차별점

| 사례 | 방식 | 치즈와의 차이 |
| --- | --- | --- |
| Marvin (`@fn`) | 런타임에 LLM 호출, docstring 기반 구현 | 치즈는 개발 시점 realize + 산출물 커밋 (런타임 무-LLM) |
| AWS Kiro | 스펙 주도 AI IDE (마크다운 스펙 → 코드) | 스펙이 언어 문법 밖에 있음 |
| GitHub Spec Kit | 스펙 주도 개발 툴킷 (마크다운) | 상동 |

차별점: **스펙을 컴파일러가 강제하는 언어 구조물로 만든 것.** requirements가 채팅 로그가 아니라 코드 옆에서 버전 관리되는 1급 문법이며, required 제약·ensure 계약을 타입체커 수준에서 집행한다.
