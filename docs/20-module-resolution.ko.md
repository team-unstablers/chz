# 모듈 해석: realize된 코드를 import하는 방법

[00 문서](00-chz-intro.ko.md)에서 `example.chz.ts`를 realize하면
`chz/realization/example/` 아래에 구현이 생긴다는 것을 보았습니다. 그런데
프로젝트의 다른 파일에서 그 구현을 쓰고 싶다면 어떻게 해야 할까요? 예를
들어 `game.ts`에서 해적 인사말 함수를 부르고 싶다면요?

이 문서는 그 질문 — "realize된 코드는 어떻게 import하나요?" — 에 답하며,
그 답의 바탕이 되는 치즈의 설계 원칙 하나를 함께 설명합니다.

## 원칙: 치즈에는 빌드 단계가 없습니다

먼저 원칙부터입니다.

> **realize가 끝난 치즈 프로젝트는, 치즈를 전혀 모르는 도구도 그대로 다룰
> 수 있는 평범한 TypeScript 프로젝트여야 합니다.**

세상에는 정말 많은 빌드 도구가 있습니다. Webpack, Vite, esbuild, React
Native의 Metro… 만약 치즈가 "import 경로를 빌드 시점에 바꿔치기하는" 식으로
동작한다면, 이 도구들 각각에 치즈 전용 플러그인을 만들어 끼워야 합니다.
그 플러그인들을 만들고 각 도구의 버전 업을 따라가며 유지보수하는 일은,
치즈를 만드는 사람에게도 치즈를 쓰는 사람에게도 재앙입니다.

그래서 치즈는 반대 방향을 선택합니다. **LLM이 관여하는 모든 일은
`chz realize`에서 끝나고, 그 결과물은 전부 평범한 `.ts` 파일로 커밋됩니다.**
빌드는 여러분이 원래 쓰던 도구가 원래 방식대로 수행합니다. 치즈 전용 빌드
명령(`chz build` 같은 것)도, 번들러 플러그인도 존재하지 않습니다.

물론 realize의 내부에서는 전처리와 tsc 연동 같은 컴파일러 작업이 일어납니다.
하지만 그것은 realize의 내부 단계일 뿐, 여러분의 빌드 파이프라인에 끼어드는
단계가 아닙니다.

## 답: 소스 파일 옆의 shim

빌드 도구가 치즈를 전혀 몰라도 되려면, import 경로는 **TypeScript의 표준
해석 규칙만으로** 목적지에 도달해야 합니다. 치즈는 이를 위해 realize가 소스
파일 옆에 작은 파일 하나를 자동 생성합니다:

```
|- example.chz.ts   # 소스 — 사람이 작성 (imagine 문법 포함)
|- example.ts       # shim — realize가 자동 생성하고 커밋
|- game.ts          # 사용처 — 사람이 작성
|- chz/
    |- realization/
        |- example/...
```

`example.ts`의 내용은 딱 한 줄입니다:

```typescript
/// example.ts — AUTO-GENERATED by chz realize. Do not edit.
export * from './chz/realization/example/implementation';
```

이제 `game.ts`는 이렇게 씁니다:

```typescript
/// game.ts
import { greetLikePirate, ShootingGame } from './example';

console.log(greetLikePirate('치즈군'));
```

`./example`이라는 경로는 TypeScript와 모든 번들러가 아는 표준 규칙에 따라
`example.ts`(shim)에 도달합니다. 소스인 `example.chz.ts`는 파일 이름이
달라서 이 경로에 걸리지 않습니다. shim은 커밋된 진짜 파일이므로 에디터
자동완성도, CI도, 어떤 번들러도 특별한 설정 없이 그대로 동작합니다.

이렇게 소스 파일 옆에 나란히 붙어 다니는 파생 파일을
**사이드카(sidecar)**라고 부르곤 합니다. 오토바이 옆에 붙은 보조 좌석처럼요.

### shim의 규칙

- **`.chz.ts` 파일은 import의 대상이 아닙니다.** 치즈 모듈의 '얼굴'은 언제나
  shim입니다. `./example.chz.ts`를 직접 import하는 것은 에러입니다.
- **shim은 파생 산출물입니다.** 직접 수정해서는 안 되며, 직접 편집은
  [60 문서](60-realize-intro.ko.md)의 '무단 드리프트'와 동일하게 해시 비교로
  감지됩니다.
- **이름 충돌은 에러입니다.** `example.chz.ts` 옆에 사람이 만든 `example.ts`가
  이미 있으면 shim을 놓을 자리가 없으므로, realize는 어느 한쪽의 이름을
  바꾸라는 에러를 출력합니다.
- **shim 생성에 LLM은 관여하지 않습니다.** 소스 파일의 위치와 이름만으로
  내용이 결정되는, 완전히 결정적(deterministic)인 산출물입니다.

### 소스 파일은 어떻게 숨기나요?

`.chz.ts` 파일에는 `imagine` 같은 확장 문법이 들어 있어서, 순수 TypeScript
컴파일러는 이 파일을 읽을 수 없습니다. 다행히 번들러는 import를 따라가며
파일을 여는데 `.chz.ts`는 아무도 import하지 않으므로, 남는 문제는 에디터와
tsc가 프로젝트 전체를 훑는 경우뿐입니다. 이것은 `tsconfig.json` 한 줄로
해결됩니다:

```json
{ "exclude": ["**/*.chz.ts"] }
```

어느 TypeScript 프로젝트에나 있는 표준 설정 항목이므로, "번들러 플러그인
없음" 원칙에 어긋나지 않습니다.

## shim이 내보내는 것 = 소스가 내보내는 것

shim은 `chz/realization/example/implementation.ts`(진입점)를 다시 내보내고,
진입점은 prologue → 구현 → epilogue 순으로 세 층을 연결합니다(60 문서 참조).
바깥에서 무엇이 보이는지에 대한 규칙은 간단합니다:

> **소스 `.chz.ts` 파일이 `export`한 것은, 그대로 shim에서도 import할 수
> 있어야 합니다.** imagine 심볼이든, 사람이 직접 작성한 타입·상수·함수든
> 마찬가지입니다.

즉 바깥에서 보면 `./example`은 마치 `example.chz.ts`가 평범한 TypeScript
파일인 것처럼 동작합니다. realize라는 과정이 있었다는 사실 자체가 사용하는
쪽에서는 보이지 않는 것이 목표입니다.

## 치즈 파일끼리도 같은 규칙입니다

`battle.chz.ts`가 `example.chz.ts`의 심볼을 쓰고 싶다면? 똑같이 shim을
import합니다:

```typescript chz
/// battle.chz.ts (발췌)
import { ShootingGame } from './example';

imagine function 보스전_시작(game: ShootingGame): void {
  requirements(`
    # 보스전을 시작하십시오.
    - 진행 중인 게임의 일반 적을 모두 제거하고 보스를 등장시켜야 합니다.
  `);
}
```

- 이 import 문은 [62 문서](62-realize-dependency-graph.ko.md)의 의존성
  그래프가 **파일 경계를 넘는 엣지**를 발견하는 단서가 됩니다. realize는
  `example.chz.ts` 쪽의 필요한 심볼을 먼저 완성한 뒤 `battle.chz.ts`를
  진행합니다.
- 파일 경계를 넘는 **순환**(A가 B를, B가 A를 import)은 v0에서는 에러로
  처리합니다. 자세한 규칙과 해결 방법은 62 문서를 참조하십시오.
- 사람 코드가 realization 디렉토리로 복사될 때(60 문서 참조), 그 안의
  `./example` 같은 상대 경로는 복사된 위치에서도 같은 파일을 가리키도록
  결정적으로 다시 계산됩니다.

## 빌드가 없다면, 검사는 누가 하나요?

빌드 단계가 없으므로 "빌드가 깨져서 알게 되는" 안전망도 없습니다. 대신
치즈는 LLM 없이 동작하는 검증 명령을 제공합니다:

```shell
$ chz verify
```

`chz verify`는 다음을 검사합니다:

- **드리프트** — realize 산출물(shim 포함)이 무단으로 편집되지 않았는지
  해시로 확인합니다(60 문서).
- **미완성 심볼** — 아직 realize되지 않았거나 실패한 imagine 심볼이 남아
  있는지 확인합니다.
- **계약** — `ensure` 계약 테스트와 realize가 남긴 테스트를 재실행합니다.

CI에서는 `chz verify`와 여러분의 평소 빌드·테스트를 나란히 돌리면 됩니다.
둘 다 LLM을 호출하지 않습니다.

> **NOTE (설계 중)**:
>
> - **첫 realize 전의 공백** — shim은 realize가 생성하므로, 한 번도
>   realize하지 않은 치즈 모듈을 import하는 코드는 그 시점에는 타입 에러가
>   됩니다. imagine 시그니처만으로 shim과 타입 스텁을 (LLM 없이) 미리
>   emit하여, '사용이 계약을 만든다'가 realize 전에도 파일 경계를 넘어
>   작동하게 하는 방안을 검토 중입니다.
> - **realization 디렉토리 이름 충돌** — 서로 다른 폴더에 같은 이름의 치즈
>   파일(`a/example.chz.ts`, `b/example.chz.ts`)이 있으면 현재의
>   `chz/realization/{이름}` 규칙이 충돌합니다. 소스 경로 구조를 미러링하는
>   방향을 검토 중입니다.
